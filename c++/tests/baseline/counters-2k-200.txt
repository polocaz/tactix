# Machine-independent by construction. Regenerated 2026-08-22: squad facing is now
# rate-limited (kFacingSlewRate) instead of snapping to the enemy direction each
# tick. Facing rotates every formation slot, so this changes where every soldier is
# told to stand and therefore the whole battle. Deliberate behavioural change, not a
# bug. stateDigest moves, and the position-dependent counters
# (candidatesExamined/cellsVisited) move with it.
#
# candidatesExamined/cellsVisited were then updated a SECOND time, for front-rank
# contact detection (Contact.cpp), which adds a neighbour query per front-rank
# soldier per tick. That update is worth distinguishing from the one above:
# stateDigest was held FIXED across it, and the fact that it did not move is the
# evidence that detection observes the battle without altering it. Nothing yet
# consumes the contact flag. If a later change to detection moves the digest
# while claiming to be observation-only, that is a bug, not a regeneration.
#
# Regenerate with:
#   tactix_bench --agents 2000 --ticks 200 --seed 42 --threads 1 --json
# Paste the six counters (candidatesExamined/cellsVisited/gridInsertions/
# jobsDispatched/squadDecisions/projectileHitTests) and stateDigest straight
# from that command's JSON output -- stateDigest below is hex, exactly as
# printed ("%016llx"), so no mental base conversion is needed. loadBaseline in
# test_counters.cpp parses stateDigest as base 16 and every other key as base
# 10, and rejects any value it cannot consume in full, so a value pasted into
# the wrong slot (or in the wrong base) fails the test loudly instead of
# silently.
#
# projectileHitTests is 0 in THIS file as of the finding-1 fix to
# selectTargetSoldier (Squads.cpp): squads no longer acquire a same-team
# target on tick 1's transient, and at 2000 agents on the default 1280x720
# field no enemy soldier is within archer range yet at 200 ticks. See
# counters-2k-1600.txt for a baseline that actually reaches combat.
#
# That companion file was counters-2k-700.txt until non-penetration landed.
# Bodies now physically resist each other, which slowed the armies' approach by
# about a third and pushed first death from tick 448 to past 1100, leaving the
# 700-tick run covering no combat at all. Renamed rather than merely
# regenerated, so the tick count in the filename cannot quietly go stale again.
#
# An intentional optimisation SHOULD change candidatesExamined/cellsVisited/
# gridInsertions/jobsDispatched/squadDecisions/projectileHitTests. Update
# them in the same commit as the change that causes it, so the diff shows the
# improvement next to its cause.
#
# stateDigest is different: it is NOT expected to move for a routine
# optimisation. It is a hash of final simulation state, so a changed digest
# means simulation *behaviour* changed -- either a deliberate behavioural
# change (update it, and say why in the commit) or a bug (a stray order-of-
# operations dependency, an uninitialised value, etc. -- do not update it
# until the cause is understood).
#
# stateDigest is also the single cross-platform correctness check: nothing
# else in this repo compares Linux and Windows output against a fixed
# reference. The determinism tests only assert same-seed reproducibility
# *within* one platform/run, never against a committed value. If CI ever
# shows Linux and Windows disagreeing on any value here -- including the
# digest -- that is a real bit-reproducibility bug, not a test problem. Do
# NOT resolve it by loosening the digest check, dropping it, or splitting
# this file per platform without a deliberate, documented decision (see spec
# Sec.5.4 for the sanctioned fallback path).
#
# A THIRD, legitimate reason the digest can move: StateDigest.hpp hashes an
# index-ordered walk of the SoA arrays (order-DEPENDENT, not order-
# independent), so a pure memory-layout change -- e.g. a future phase that
# reorders agent arrays by spatial cell for cache locality, with no change to
# *which* agents exist or *what* they do -- will necessarily move the digest
# even though simulation behaviour is unchanged. That is expected, not a bug.
# If you land a layout-only reordering, update stateDigest here in the same
# commit and say explicitly in the commit message that the move is a layout
# change, not a behavioural one, so this stays distinguishable from case 2
# above in history.
# Regenerated 2026-08-22 for the troop-class model. Discipline moved out of three
# per-UnitType constants into a column of kTroopLoadout (Loadout.hpp), so Team A
# legionaries now stand at 0.90 and Team B hoplites at 0.85 where both were 0.85
# before. Discipline scales formation compression (squadCompression in
# Soldiers.cpp), so every soldier is told to stand somewhere slightly different
# and the whole battle follows. Deliberate behavioural change, not a bug.
